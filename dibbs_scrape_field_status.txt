SCOPE OF THIS LIST
------------------
Of the 121 DIBBS export fields, 30 require data that originates from the
DIBBS solicitation itself (not from the vendor's quote, not a static
profile value, and not reserved/blank). These 30 split into two groups:

  GROUP A (22 fields) - value is copied straight from the solicitation into
                         the export record.
  GROUP B (8 fields)  - the RFQ's own value must be scraped so the vendor's
                         quoted value can be validated/compared against it
                         (FOB point/city/state/country, inspection point,
                         inspection CAGEs, delivery days). The export column
                         itself holds the vendor's answer, but the app cannot
                         judge compliance (or set Bid Type BW/AB correctly)
                         without knowing the RFQ's original value.

Status legend:
  [SCRAPED]     - a Solicitation model field exists AND extractSolicitations.py
                   actively populates it.
  [NOT SCRAPED] - no model field, or a model field exists but is not actually
                   populated from the scrape (see notes).

NOTES / CAVEATS
----------------
1. This assessment reflects what solicitations/models.py (Solicitation) and
   extractSolicitations.py actually implement as of this review. It does not
   cover extractSolicitationsOld.py or any other legacy/unused script.
2. Several "not scraped" fields (052-055, the AIDC block) only apply to
   Solicitation Type Indicator = "I" (Automated Indefinite Delivery
   Contract) solicitations — but since #002 itself isn't scraped, the app
   currently has no way to know when that condition even applies.
3. Fields in Group B are not necessarily meant to be copied verbatim into
   the export (the vendor's own FOB/inspection terms go into the column);
   they are listed because the RFQ's original value must still be known to
   run DIBBS's required comparison/Bid-Type-exception logic correctly.
